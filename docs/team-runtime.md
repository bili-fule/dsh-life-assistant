# 多 Agent 编排：实现与验证记录

更新：2026-10-21（0.34.0）。当前为本地开发实现，生产运行 0.25.0（见部署验收记录）。本文区分真实运行时验证、测试替身与未完成项目。

## 当前实现

主 QQ Agent 可以通过 `team_delegate` 分派聊天或公开研究，自己继续原生活动。任务需要关联当前范围的活跃关切，保存分工理由和完成／停止条件；可选 `choiceId` 把分工挂到自己的某次选择上，但不能让同一活动因执行者数量重复计入满足。`team_deliberate` 提供当前可见的关切、任务与报告；`team_review` 记录主 Agent 的判断，不自动把报告认定为成功，不循环启动任务。

每个执行者使用独立 DSH SDK 进程、HOME、DSH_HOME 和工作目录。模型只看到该角色工具；工具执行前仍由宿主检查任务、视图和租约。普通聊天和研究没有 shell、宿主文件和派生 Agent 工具。此处是进程与工具隔离，尚不是独立 OS 用户或容器隔离；现有工程排障继续使用原来的独立容器。

聊天执行者可以读取指定窗口、召回同范围记忆、等待实际新消息、发送消息和增量报告。等待工具在宿主等待，遵循新消息的五秒窗口，不使用不断唤醒模型的定时提示。研究执行者可读取公开网页及报告。公开研究与工程任务**由宿主自建 public 视图**：主体在任意窗口都能分派，但任务拿不到任何私有材料，因此不需要先切窗口也不存在「忘了切 public 就分派失败」。

分支属于同一个主体：`chat` / `reader` / `peer` 任务沿用调用方的视图，而视图的范围是该平台**全部已授权窗口**（见 [连续主体](subject-continuity.md)）。所以分支能读到主体在别的窗口已经知道的事、共享同一份活动与关切，但读不到另一个主体（微信）的任何资料。任务自己的发言租约与工具集仍然独立。

同一窗口只有一个发言租约。主 Agent 接管、任务完成、取消、过期和撤权都会使旧发送失效。聊天发送使用任务内稳定 replyId；网络结果不明时保留 uncertain，不自动重发，也不伪造成功回执。主 Agent 已排队的消息同样检查其原租约版本。

执行者可以把自己真正读到的材料放到任务证据板（`team_evidence` / `team_board`），证据沿用任务的资料来源范围：同一主体的其他窗口可以看，另一个主体的视图看不到；主 Agent 用 `team_inspect` 或 `team_deliberate` 查看。同一任务里同一来源的同一段话只算一条证据（重复提交返回原编号并标 `duplicate`），同一来源的不同说法会保留并标 `conflict`，让分歧可见而不是被平均掉。执行中可以用 `team_steer` 追加一条有界提示，宿主在下一个原生边界交给执行者一次，不扩大权限，也不改变全局人设。

后一个任务常常需要前一个任务真正读过的东西：`team_search` 按线索跨任务检索当前窗口可见的证据板，返回任务编号、类型、来源与摘录，摘录不代表结论已被验证；它用与证据板相同的范围规则，因此不会读到另一个主体的材料。

## 分支之间的增量事件

分支不只在结束时汇报。每次 report 写成一条 `progress` 事件，每次 `team_evidence` 的 `finding` 写成一条 `finding` 事件，任务结束与取消分别写成 `completed` / `cancel`。事件写进 `yoyo_team_events`，数据库是权威；`dedupe_key` 保证同一条消息只写一次，`expires_at` 保证迟到的提问不再冒充新问题。

投递靠游标：分支在原生 `step` 边界向宿主取一次（`TeamCoordinator` 把 `events` 和 `steers` 一起返回），宿主随即推进 `yoyo_team_cursors`，所以同一条事件不会送两次，进程重启后从上次确认的位置继续，而不是重放全部历史。分支只收到自己信箱 `task:<id>`、所属活动 `activity:<id>` 与主体频道 `subject` 的事件，不会收到自己写的那条。

同级问答走同一总线：`team_ask` 写入 `question`，宿主知道调用者是谁，模型不能冒充别的分支或主体；被问的分支在下一个原生边界收到，用 `team_answer` 回答，答复的 `ref` 指回原问题，提问方在下次边界收到 `answer`。整个过程没有主 Agent 转述。`team_events` 查当前范围内的事件流与仍未回答的问题；`state().team` 只给并发数、分支状态、等待原因、未答问题数量和最近事件的元数据，不给正文。

三种状态分开记：事件已写入、已送达（游标推进且 `delivered_count` 增加）、分支据此行动（它下一份 report/evidence）。把「写了」当成「收到」是本项目明确不接受的简化。

同一来源被不同任务读到、说法却不一致时，分歧要能看见：`team_sources` 按来源汇总本窗口可见的证据，给出被读过几次、有几种不同说法、分别是哪几个任务读的，`conflict:true` 表示存在不同说法。这张表直接由证据行算出，不另存一份真相，因此不会和证据板不一致；没有来源标注的证据不会进入这张表。它只说明「材料互相矛盾」，不代表任何一方已被核实。

## 执行者的记忆候选

执行者可以提交记忆候选（`team_remember`），但候选不是记忆：它连同真实来源一起存进 `yoyo_team_memory_candidates`，等主体回到同一个窗口时用 `team_memory` 决定。

- 来源必须是真实消息编号、工具回执或网页编号，空来源直接拒绝；同一候选不会重复排队。
- 执行者不能提交关于某人身份或表达习惯的候选：它的窗口能证明「说过什么」，不能证明「这个人是谁」。
- 采纳时由记忆层在主体自己的视图里重新核对原文，**置信类型固定为 `worker_report`**，所以交上来的内容不会因为被采纳就变成观察；来源失效则采纳失败、候选仍保持待决定。
- 不采纳要写理由，理由与原候选一起保留；处理过的候选不能再处理一次。
- 候选与处理结果都按范围过滤：别的窗口既看不到候选，也无法决定它。

现阶段已支持增量报告、任务级证据板、跨任务证据检索、来源去重与冲突标记及跨任务来源登记、执行者记忆候选与主体决策、任务的记忆包、运行中追加提示、任务级用量台账、执行者身份复用与六种角色（含与主体几乎同等的 `peer`）；尚未实现容器级资源隔离、执行者的排障能力与真实模型下的连续观察。

## 任务的记忆包

分派时可以给一条线索（`team_delegate` 的 `recall`）。宿主用记忆层在**分派窗口**里召回最多 5 条摘要，存进 `yoyo_team_memory_packs`，执行者在第一次原生边界通过桥接拿到它，作为上下文显示一次。

- 只有摘要：标题、发生了什么、来源条数、置信类型都在，但原文要它自己用 `team_recall` 或证据板核对，摘要不能当作新证据。
- 只有这个任务的任务编号能取到它，包的范围是分派窗口的范围；别的窗口读不到，也不会因为任务换了视图而扩大。
- 同一任务重复组装会替换旧包，不会堆叠；召回为空时也如实记录「线索给了、没找到」。
- 记忆层没启用时不会静默假装已交底：分派结果里直接给出 `memoryPack.error`。
- `team_inspect` 可以查看这个任务实际拿到的包，用于判断它是在有依据地说，还是在猜。

| 角色 | 能做什么 | 边界 |
| --- | --- | --- |
| `chat` | 在指定窗口阅读、等待、召回、发言、报告、提交证据、提交记忆候选、读自己的记忆包 | 唯一持有发言租约的角色 |
| `research` | 阅读公开网页、报告、提交证据、提交记忆候选、读自己的记忆包 | 只能从 public 视图分派，无窗口、不能发言 |
| `reader` | 在指定窗口只读、召回、报告、提交证据、提交记忆候选、读自己的记忆包 | 不取发言租约，不能发言 |
| `verify` | 看证据板、召回、读自己的记忆包、指出证据不足或矛盾 | 不新增来源、不能提交候选、不能发言 |
| `engineer` | 在隔离环境里跑 Node／Python／Shell，查看自己任务的作业结果，提交证据与报告 | 只能从 public 视图分派，不能发言、读不到窗口、拿不到宿主文件与排障容器 |
| `peer` | 与主体几乎同等：阅读、搜索、原文分页、文件与附件、合并转发、公开网页、代码执行、记忆召回／核对／提案／分段／概括，并可在任务窗口发言 | 没有控制面：不能分派或取消其他执行者、不能改主体的注意力与人设、不能撤回记忆、进不了排障容器；始终可被主体取消、追加提示与接管 |

每个角色的可选方法与宿主分发时的一致；任务可以**缩小**自己的工具集（`toolset`），不能扩大。

## 工程角色

`engineer` 让执行者能做真正的工程动作，但只在最保守的形态下：`team_execute` 把代码交给与主 Agent `yoyo_execute` 同一个隔离执行服务（无网络、项目白名单、输出需显式声明），`team_job` 读自己任务的作业状态、标准输出与导出文件。

- 只能从 **public** 视图分派：私人聊天内容不会进代码执行环境，理由和「公开研究只能从 public 视图发起」一致。
- 拿不到 shell、宿主文件、宿主浏览器和独立排障容器；排障作业（`backend='debug'`）对执行者直接关闭，仍只属于主 Agent。
- 同一任务提交同一段代码会被哈希成同一个幂等键，重试不会扇出重复作业；作业行按视图范围入库，别的窗口读不到私人范围内的作业。
- 执行者不能发言、不能读窗口，结果只能通过 `team_evidence`／`team_report` 回到任务证据板，由主 Agent 判断。
- 隔离执行服务未配置时直接报「隔离执行服务未配置」，不会假装跑过。

容器级隔离仍未实现：这里是进程与工具白名单隔离，不是容器。

## 同伴执行者

`peer` 是「与主体几乎同等」的角色。它不复制实现，而是**复用主体自己的工具实现**：宿主在注册主体工具时，把允许外借的那几件（阅读、搜索、原文分页、文件、附件、合并转发、公开网页、记忆召回／核对／提案／分段／概括）映射成执行者可达的版本，调用时换上**任务的视图**和**任务级的回执编号**——所以执行者的读、搜、查都会像主体一样留下可引用的 receipt，也能被 `team_inspect` 与来源登记看到。

它没有的东西同样明确，而且不是靠提示词约束：

- **控制面**：分派／取消／接管其他执行者（`team_*` 全套）、切换关注窗口、设置注意力与免打扰（`yoyo_open`／`yoyo_attention`／`yoyo_mute`／`yoyo_dismiss`）。
- **主体的自身状态**：活动、打算、情绪与动机、关切与反馈、学习意图、人设与设置。
- **不可逆动作**：记忆撤回（`memory_retract`）与排障容器（`yoyo_debug*`）仍只属于主体。
- 发言仍走任务自己的发言租约：主体 `team_takeover` 之后，同伴的后续发送立刻失效；它同样受 `max_steps`、任务期限、用量台账与暂停开关约束。

换句话说：**能力接近同等，控制权仍然单线**。任务契约还记录 `parent_id`、`depends_on`、`authorization_version`、`persona_version` 与 `max_steps`：创建时的授权版本快照一旦过期，旧任务就不能领取；依赖未完成的任务既不会在调度里启动，也不能被领取；`max_steps` 覆盖全局每任务步数上限。

执行者的身份由任务编号派生（`worker-` + 哈希前缀），因此同一个任务的后续尝试会复用它的 DSH 工作目录与原生会话，而不是每轮换一个陌生人。每一步都会续租，租约在硬上限内延长；期限检查改为按续租后的实际时间判断。失败会记入 `failures` 并有界安排重试：默认关闭（`retryBlocked`），打开后只对到期且未超出尝试次数的任务重排；发送状态为 `uncertain` 或 `sending` 的任务永不自动重试，重启产生的阻塞也不会自动续跑。

执行者的每一步与 Token 用量都记在 `yoyo_team_usage`（按任务与尝试分行），日预算另记在 `yoyo_usage`。计数在宿主数据库里，重启或换一个宿主实例都不会重新发放预算；超额的那一步被拒绝，执行者随之阻塞。`team_overview` 只给每步数与 Token 汇总，不含目标与正文；`team_inspect` 与 `team_deliberate` 在原资料范围给完整用量。执行者的原生运行时若未报告 Token，就记 0，不估算。

「没有上报」和「确实为 0」分开记录：`yoyo_team_usage.tokens_reported` 只在运行时真的报过正数 Token 时置位。`usage()` 返回 `tokensReported` 与 `note`——未上报时 `note` 明确写「0 表示未测量，不代表没有消耗」，管理页也显示「Token 未上报」而不是一个会误导人的 0。适配器依次尝试 `usage.totalTokens / total / outputTokens`，仍取不到就如实标为未上报；老库里已有的正数 Token 在升级时补标为已上报，因为旧代码只在真实回报后才写入。

## 动机模型的准确边界

现有 `yoyo_concern` 保存起因、价值、下一步和完成／停止条件；新增团队意图记录关联这些关切。执行者报告始终标为 worker_report，主 Agent 的解读仍是判断。不会因为执行进程结束就自动把关切设为完成。同理，`team_review` 的 `done` 只表示这次任务做完了，它不会把关切唤醒记成有效；只有关切层面的决定（`yoyo_feedback` 或把关切改成 done／abandoned）才算。

用户已确认无需复原最初的五维向量。新方向是以开心与持续满足为主要目标，参考心理学区分期待、体验和偏好学习，见 [自主动机 Plan](plans/humanlike-motivation-plan.md)。该方案阶段 1–4 已实现：四个 `self_*` 工具记录期待、体验和偏好，`team_delegate` 可以关联某次选择，经历按真实事件去重；阶段 5 的真实运行验收未完成。当前五类满足记录与关切关联不等于新动机系统，两者并存。

## 数据与恢复

`yoyo_team_tasks` 记录任务与执行者身份，`yoyo_team_speakers` 记录窗口发言版本，`yoyo_team_reports` 保存有范围的报告，`yoyo_team_evidence` 保存任务范围内的证据片段，`yoyo_team_steers` 保存一次性追加提示，`yoyo_team_usage` 保存每个任务与尝试的步数与 Token，`yoyo_team_intents/reviews` 连接关切和复查，`yoyo_team_deliveries` 保存实际发送状态。全局总览仅返回不含正文的任务元数据与用量汇总。

服务重启将未结束的工作设为 blocked 并计入一次 interruption，撤销旧租约；不盲目重放执行。未确认发送转 uncertain，旧记录保留。完成或阻塞形成一次可消费的事件，主 Agent 在空闲时回到原授权范围查看；忙碌时不取消现有工作。停服务先结束执行者，再关闭数据库。

可恢复的多轮执行需要三项同时成立：同一执行者身份（同一工作目录与原生会话）、按步续租的心跳、以及显式的重试开关。默认三者中只有前两项启用，自动重试保持关闭，避免重启后重复发信。

## 管理视图

`autonomy.team` 在动态状态里给出运维视角，只看「谁在跑、卡在哪、花了多少」，不暴露任务目标与报告正文：

- `concurrency.running / concurrency.max`：当前在跑的执行者数与上限；
- `tasks[]`（按创建时间倒序，最多 50 条）：任务编号、角色、状态、尝试次数、失败次数、重试时间、续租时间、到期时间、已跑步数与 Token、报告与证据条数、租约持有目标与到期时间、依赖任务数，以及 `waitReason`（例如「等待重试」「失败，等待复查」「等待依赖任务」「执行中（无发言租约）」「等待对方回复」）。

这份视图不含消息正文，可以直接给管理页使用；真正的复核仍要回到任务范围内的 `team_board` 与 `team_usage`。

管理页（`/` → 「yoyo 的活动」→「团队编排」）已经渲染这份状态：在跑并发数、每个任务的编号前缀、角色、状态与等待原因、尝试与失败次数、计划重试时间、步数与 Token（未上报时显示「未上报」）、报告与证据条数、租约到期时间、依赖数量。**任务目的与报告正文默认不展示**：要在页面点「查看资料」并二次确认后，才通过 `POST /api/yoyo/team-detail` 读取**那一个**任务的资料（目的、报告、证据板、记忆包、用量）。

这条通道有三条硬约束：一次只返回一个任务，不做跨窗口汇总；宿主会用该任务自己的 `view_id` 重新校验窗口**现在仍然有效**，撤销授权后立刻读不到；页面拿不到任何窗口的清单，只能按任务编号逐个点。也就是说，页面的可见性跟着资料范围走，而不是跟着管理密钥走。

页面上的操作走同一个管理端点 `POST /api/yoyo/team`：`steer`（给进行中的任务追加一条提示，执行者下一个原生边界收到一次）、`takeover`（接管该窗口发言权，旧执行者后续发送失效）、`cancel`（取消任务并撤销发言权）。端点只接受任务编号，宿主按该任务自己的 `view_id` 解析范围，**不借用**当前页面的其它权限；不存在的任务、未知操作、已结束任务都会被拒绝。

## 配置契约

仅在独立 QQ 的 autonomy 配置中启用 `team.enabled`。需要管理员提供：

- `root`：独立执行者目录，不能与生产 DSH_HOME 重合。
- `sdkModule`：已安装的 `@deepseek-ai/dsh-sdk-client` 的绝对入口路径。
- `providerPatch`：单独的模型路由 patch，不使用包含微信或生产插件的整体配置。
- `provider`、`model`：执行者模型路由。
- `env`：显式需要的模型代理环境变量；不会继承整个主服务环境。
- `maxConcurrent`：默认 2；`maxSteps`：默认每任务 20 步；`maxTokens`：默认输出上限 8000。
- `leaseMs`：每步续租后的租约长度，默认 900000，硬上限一小时。
- `retryBlocked`：默认 false。打开后允许按 `retryAttempts`（默认 1）与 `retryDelayMs`（默认 60000）重排失败任务；未确认发送的任务不会重排。

执行者计入现有 QQ dailySteps 预算，暂停状态会阻止后续模型步骤和发送。聊天工具权限不意味着允许工程操作。

生产启用前仍需准备独立运行目录、模型路由、资源限制，并在真实模型下验证完整对话行为。当前没有自动修改生产配置。
