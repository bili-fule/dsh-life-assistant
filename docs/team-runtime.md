# 多 Agent 编排：实现与验证记录

更新：2026-10-21（0.24.0）。当前为本地开发实现，生产配置默认关闭。本文区分真实运行时验证、测试替身与未完成项目。

## 当前实现

主 QQ Agent 可以通过 `team_delegate` 分派聊天或公开研究，自己继续原生活动。任务需要关联当前范围的活跃关切，保存分工理由和完成／停止条件；可选 `choiceId` 把分工挂到自己的某次选择上，但不能让同一活动因执行者数量重复计入满足。`team_deliberate` 提供当前可见的关切、任务与报告；`team_review` 记录主 Agent 的判断，不自动把报告认定为成功，不循环启动任务。

每个执行者使用独立 DSH SDK 进程、HOME、DSH_HOME 和工作目录。模型只看到该角色工具；工具执行前仍由宿主检查任务、视图和租约。普通聊天和研究没有 shell、宿主文件和派生 Agent 工具。此处是进程与工具隔离，尚不是独立 OS 用户或容器隔离；现有工程排障继续使用原来的独立容器。

聊天执行者可以读取指定窗口、召回同范围记忆、等待实际新消息、发送消息和增量报告。等待工具在宿主等待，遵循新消息的五秒窗口，不使用不断唤醒模型的定时提示。研究执行者可读取公开网页及报告。公开研究只能从 public 视图发起，暂不支持私有材料的脱敏公开搜索。

同一窗口只有一个发言租约。主 Agent 接管、任务完成、取消、过期和撤权都会使旧发送失效。聊天发送使用任务内稳定 replyId；网络结果不明时保留 uncertain，不自动重发，也不伪造成功回执。主 Agent 已排队的消息同样检查其原租约版本。

执行者可以把自己真正读到的材料放到任务证据板（`team_evidence` / `team_board`），证据沿用任务的资料来源范围，其他窗口和公开视图看不到；主 Agent 用 `team_inspect` 或 `team_deliberate` 查看。同一任务里同一来源的同一段话只算一条证据（重复提交返回原编号并标 `duplicate`），同一来源的不同说法会保留并标 `conflict`，让分歧可见而不是被平均掉。执行中可以用 `team_steer` 追加一条有界提示，宿主在下一个原生边界交给执行者一次，不扩大权限，也不改变全局人设。

后一个任务常常需要前一个任务真正读过的东西：`team_search` 按线索跨任务检索当前窗口可见的证据板，返回任务编号、类型、来源与摘录，摘录不代表结论已被验证；它用与证据板相同的范围规则，因此不会读到别的窗口的材料。

## 执行者的记忆候选

执行者可以提交记忆候选（`team_remember`），但候选不是记忆：它连同真实来源一起存进 `yoyo_team_memory_candidates`，等主体回到同一个窗口时用 `team_memory` 决定。

- 来源必须是真实消息编号、工具回执或网页编号，空来源直接拒绝；同一候选不会重复排队。
- 执行者不能提交关于某人身份或表达习惯的候选：它的窗口能证明「说过什么」，不能证明「这个人是谁」。
- 采纳时由记忆层在主体自己的视图里重新核对原文，**置信类型固定为 `worker_report`**，所以交上来的内容不会因为被采纳就变成观察；来源失效则采纳失败、候选仍保持待决定。
- 不采纳要写理由，理由与原候选一起保留；处理过的候选不能再处理一次。
- 候选与处理结果都按范围过滤：别的窗口既看不到候选，也无法决定它。

现阶段已支持增量报告、任务级证据板、跨任务证据检索、来源去重与冲突标记、执行者记忆候选与主体决策、任务的记忆包、运行中追加提示、任务级用量台账、执行者身份复用与四种角色；尚未实现跨任务的冲突登记表（同一来源在不同任务里的分歧目前只在本任务内可见）与活动级评价汇总。

## 任务的记忆包

分派时可以给一条线索（`team_delegate` 的 `recall`）。宿主用记忆层在**分派窗口**里召回最多 5 条摘要，存进 `yoyo_team_memory_packs`，执行者在第一次原生边界通过桥接拿到它，作为上下文显示一次。

- 只有摘要：标题、发生了什么、来源条数、置信类型都在，但原文要它自己用 `team_recall` 或证据板核对，摘要不能当作新证据。
- 只有这个任务的任务编号能取到它，包的范围是分派窗口的范围；别的窗口读不到，也不会因为任务换了视图而扩大。
- 同一任务重复组装会替换旧包，不会堆叠；召回为空时也如实记录「线索给了、没找到」。
- 记忆层没启用时不会静默假装已交底：分派结果里直接给出 `memoryPack.error`。
- `team_inspect` 可以查看这个任务实际拿到的包，用于判断它是在有依据地说，还是在猜。

| 角色 | 能做什么 | 边界 |
| --- | --- | --- |
| `chat` | 在指定窗口阅读、等待、召回、发言、报告、提交证据、提交记忆候选、读自己的记忆包 | 唯一持有发言租约的角色 |
| `research` | 阅读公开网页、报告、提交证据、提交记忆候选、读自己的记忆包 | 只能从 public 视图分派，无窗口、不能发言 |
| `reader` | 在指定窗口只读、召回、报告、提交证据、提交记忆候选、读自己的记忆包 | 不取发言租约，不能发言 |
| `verify` | 看证据板、召回、读自己的记忆包、指出证据不足或矛盾 | 不新增来源、不能提交候选、不能发言 |

每个角色的可选方法与宿主分发时的一致；任务可以**缩小**自己的工具集（`toolset`），不能扩大。任务契约还记录 `parent_id`、`depends_on`、`authorization_version`、`persona_version` 与 `max_steps`：创建时的授权版本快照一旦过期，旧任务就不能领取；依赖未完成的任务既不会在调度里启动，也不能被领取；`max_steps` 覆盖全局每任务步数上限。

执行者的身份由任务编号派生（`worker-` + 哈希前缀），因此同一个任务的后续尝试会复用它的 DSH 工作目录与原生会话，而不是每轮换一个陌生人。每一步都会续租，租约在硬上限内延长；期限检查改为按续租后的实际时间判断。失败会记入 `failures` 并有界安排重试：默认关闭（`retryBlocked`），打开后只对到期且未超出尝试次数的任务重排；发送状态为 `uncertain` 或 `sending` 的任务永不自动重试，重启产生的阻塞也不会自动续跑。

执行者的每一步与 Token 用量都记在 `yoyo_team_usage`（按任务与尝试分行），日预算另记在 `yoyo_usage`。计数在宿主数据库里，重启或换一个宿主实例都不会重新发放预算；超额的那一步被拒绝，执行者随之阻塞。`team_overview` 只给每步数与 Token 汇总，不含目标与正文；`team_inspect` 与 `team_deliberate` 在原资料范围给完整用量。执行者的原生运行时若未报告 Token，就记 0，不估算。

## 动机模型的准确边界

现有 `yoyo_concern` 保存起因、价值、下一步和完成／停止条件；新增团队意图记录关联这些关切。执行者报告始终标为 worker_report，主 Agent 的解读仍是判断。不会因为执行进程结束就自动把关切设为完成。

用户已确认无需复原最初的五维向量。新方向是以开心与持续满足为主要目标，参考心理学区分期待、体验和偏好学习，见 [自主动机 Plan](plans/humanlike-motivation-plan.md)。该方案阶段 1–4 已实现：四个 `self_*` 工具记录期待、体验和偏好，`team_delegate` 可以关联某次选择，经历按真实事件去重；阶段 5 的真实运行验收未完成。当前五类满足记录与关切关联不等于新动机系统，两者并存。

## 数据与恢复

`yoyo_team_tasks` 记录任务与执行者身份，`yoyo_team_speakers` 记录窗口发言版本，`yoyo_team_reports` 保存有范围的报告，`yoyo_team_evidence` 保存任务范围内的证据片段，`yoyo_team_steers` 保存一次性追加提示，`yoyo_team_usage` 保存每个任务与尝试的步数与 Token，`yoyo_team_intents/reviews` 连接关切和复查，`yoyo_team_deliveries` 保存实际发送状态。全局总览仅返回不含正文的任务元数据与用量汇总。

服务重启将未结束的工作设为 blocked 并计入一次 interruption，撤销旧租约；不盲目重放执行。未确认发送转 uncertain，旧记录保留。完成或阻塞形成一次可消费的事件，主 Agent 在空闲时回到原授权范围查看；忙碌时不取消现有工作。停服务先结束执行者，再关闭数据库。

可恢复的多轮执行需要三项同时成立：同一执行者身份（同一工作目录与原生会话）、按步续租的心跳、以及显式的重试开关。默认三者中只有前两项启用，自动重试保持关闭，避免重启后重复发信。

## 管理视图

`autonomy.team` 在动态状态里给出运维视角，只看「谁在跑、卡在哪、花了多少」，不暴露任务目标与报告正文：

- `concurrency.running / concurrency.max`：当前在跑的执行者数与上限；
- `tasks[]`（按创建时间倒序，最多 50 条）：任务编号、角色、状态、尝试次数、失败次数、重试时间、续租时间、到期时间、已跑步数与 Token、报告与证据条数、租约持有目标与到期时间、依赖任务数，以及 `waitReason`（例如「等待重试」「失败，等待复查」「等待依赖任务」「执行中（无发言租约）」「等待对方回复」）。

这份视图不含消息正文，可以直接给管理页使用；真正的复核仍要回到任务范围内的 `team_board` 与 `team_usage`。

## 配置契约

仅在独立 QQ 的 autonomy 配置中启用 `team.enabled`。需要管理员提供：

- `root`：独立执行者目录，不能与生产 DSH_HOME 重合。
- `sdkModule`：已安装的 `@deepseek-ai/dsh-sdk-client` 的绝对入口路径。
- `providerPatch`：单独的模型路由 patch，不使用包含微信或生产插件的整体配置。
- `provider`、`model`：执行者模型路由。
- `env`：显式需要的模型代理环境变量；不会继承整个主服务环境。
- `maxConcurrent`：默认 2；`maxSteps`：默认每任务 20 步；`maxTokens`：默认输出上限 8000。
- `leaseMs`：每步续租后的租约长度，默认 900000，硬上限一小时。
- `retryBlocked`：默认 false。打开后允许按 `retryAttempts`（默认 1）与 `retryDelayMs`（默认 60000）重排失败任务；未确认发送的任务不会重排。

执行者计入现有 QQ dailySteps 预算，暂停状态会阻止后续模型步骤和发送。聊天工具权限不意味着允许工程操作。

生产启用前仍需准备独立运行目录、模型路由、资源限制，并在真实模型下验证完整对话行为。当前没有自动修改生产配置。

## 已验证

`test/team-store.test.mjs` 与 `test/team-host.test.mjs` 验证跨窗口隔离、同窗单发言者、接管后的晚到发送、权限撤回、过期任务、持久化、取消、发送幂等、缺少回执、网络不确定结果、主 Agent 排队消息的旧租约，动机分工和复查，任务级证据板只在本任务视图可见、追加提示只送达一次、取消后不能再追加，按任务与尝试分行的用量台账在重启后不重置，租约续租有硬上限、重试次数有界、发送不确定的任务不会被重排，同一任务的重试复用同一执行者身份，读者与核对者不取发言租约且工具集只能缩小，授权版本变化后旧任务不能领取，依赖未完成的任务不能被领取，运维状态只给执行者、租约、用量与等待原因而不含任务正文，同一来源的同一段话只登记一条证据、不同说法标为冲突，跨任务检索只在当前窗口范围内返回并可供工具调用，执行者的记忆候选在主体采纳前不是记忆、采纳后固定记成执行者报告、不采纳需理由且只处理一次，任务记忆包只装本窗口召回的摘要、只由该任务读取、重复组装即替换、记忆层未启用时明确报错。`test/motivation.test.mjs` 另验证动机选择关联分派：跨范围、已结束以及未启用动机层的情形都被拒绝。

`test/team-native-smoke.mjs` 是显式运行的集成测试：使用已安装的 DSH SDK 0.2.0-rc.2，同时启动两个真实 DSH 子进程，并用脚本化测试模型执行聊天发送工具和公开网页工具。工具由本地测试宿主接收，不向真实 QQ 或真实网站发送测试请求。它验证原生循环、模型工具 schema、隔离环境变量、工具桥和最终报告，不证明真实模型已经正确进行社交判断。

运行方式：`node test/team-native-smoke.mjs <SDK 的 lib/index.js 绝对路径>`。测试轨迹保存在临时目录，输出位置供复核，不包含生产凭据。

## 后续目标

2026-10-21 的代码审计按优先级列出尚未实现的编排能力；共享证据板、运行中追加提示、任务级用量台账、执行者身份复用与角色契约已在 0.14.0–0.17.0 补齐，运维状态视图在 0.21.0 补齐，跨任务证据检索与来源去重／冲突标记在 0.22.0 补齐，执行者记忆候选在 0.23.0、任务记忆包在 0.24.0 补齐，动机层本身已实现阶段 1–4：

1. 跨任务的来源冲突登记表、活动级评价汇总与关切侧的有效／无效唤醒计数（记忆层已有提醒效果计数，团队侧尚未汇总到关切）。
2. 管理页前端（后端 `autonomy.team` 状态已就绪）、容器级资源隔离（当前是进程与环境隔离）。

4. 真实模型下的多轮续跑、阅读者与核对者的实际质量观察；目前只有确定性测试。
