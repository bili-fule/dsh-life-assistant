**这次真实运行抓到两个确定性测试没抓到的问题（都已修并补测试）：**
1. **执行者的 `read`/`recall` 被 peer 桥整体替换**：主体没有 peer 桥时，聊天/只读执行者直接「工具未启用」，真实模型于是读不到群、只能放弃（首次运行结果就是 `abandoned`）。修法：peer 桥存在时仍优先用它，缺失时 `read`/`recall` 回落到宿主自己的实现；补测试「a branch can still read its own window when the subject has no peer bridge」（`test/chat-routing.test.mjs`）。
2. **预算耗尽会伪装成失败**：首轮 `maxSteps 8` 被模型用完，任务以 `blocked` 结束、意图被映射成 `abandoned`。该脚本预算调到 10 后正常完成；教训是「预算耗尽」必须显示为暂停/受阻而不是放弃，与显式完成契约一致。
3. **两个原生脚本在显式完成契约之后失效**（`13e98e4` 引入）：`test/team-native-smoke.mjs` 与 `test/team-native-events.mjs` 的脚本化模型在回合结束时只输出文字、不调用 `team_finish`，于是守卫转向（steer）使回合以非 `completed` 结束，任务被判失败。已按新契约改成显式 `team_finish`，两个脚本重新 `PASS`（2026-10-21 21:58）。这说明「守卫」这类全局契约必须同时更新脚本化模型，否则所谓集成测试会静默失效。

## 这一轮真实运行暴露并修掉的两件事

**1. 缺「等兄弟分支事件」的宿主原语（已修）。** 第一次运行时，答复分支在自己的第一个边界查了一次事件（那时问题还没写），报告「没有需要回答的问题」并结束，问题随后写出就再没人读。确定性测试没暴露它，因为脚本模型被写成「查到就答」，而真实模型会按「没事就结束」行动。

修法：`team_wait_event(seconds)` —— 宿主在 SQLite 上有界等待（最长 30 秒、每 100 ms 检查一次，不唤醒模型），拿到事件就连同投递游标一起交给分支，超时明确返回「这段时间没有可领取的事件」。分支不再早退，也不需要空转轮询。

**2. 「回答哪个问题」不能靠模型抄编号（已修）。** 第二次运行时答复分支等到了问题，但两次 `team_answer` 被拒：模型把问题原话当成参数传了，而宿主只按事件编号查找。修法：`answer` 先按编号找，找不到就取「发给这个任务的、最新的未答问题」；归属仍由宿主判定，模型无法回答别人的问题。

## 数值怎么读

- 并行墙钟 9.4 s 对串行 46.2 s，差距来自两个分支同时读材料与生成；样本只有一次、任务很小，**不能**外推成「并行总是快五倍」。
- 真实模型的步数与延迟随内容波动（两次并行分别跑了 21 s 和 9.4 s），所以这里只记录同一次对照内的相对关系。
- Token 早期未接计量；2026-10-21 22:0x 起改为从原生 `assistant/message` 事件里的 `usage` 汇总，已经能给出实测值（见上文与下文表格）；运行时确实没上报的尝试仍标为「未测量」，不写 0。

## 追加：聊天续接的真实模型运行（同日 22:0x）

`node test/team-native-chat.mjs`：一个真实模型聊天执行者，先读群、回复、`team_pause` 挂起，随后被两条真实新消息唤醒，**同一个常驻会话**继续处理。

| 项 | 结果 |
| --- | --- |
| 运行次数 | 2 次提示，1 次唤醒，`resident=true`（没有第二次 create Session） |
| 唤醒简报 | `count=2`、`after=2`，消息原文随简报送达 |
| 游标 | 从 2 推进到 5；第二次 `team_read` 的 `after` 正是上次游标，读到 #3–#5 |
| 发送 | 2 条真实消息、2 条投递记录；模型在一次尝试里复用旧回复编号时被宿主拒绝（`回复编号已用于其他内容`），没有重复发送 |
| 终态 | 再次 `suspended`（继续等后续），不是伪完成 |
| 步数 | 7 步（两次提示合计） |
| Token | `tokensReported=false`（未测量，不记为 0） |

**这轮真实运行又暴露了两个问题（已修并补测试）：**

1. **跨进程不能复用 Session**：`test/team-native-resume-probe.mjs` 实测「同一进程内同 id 第二次提示成功（事件继续累积）」，而「新进程用已存在的 id」直接报 `session "…" already exists`。因此聊天任务改为**常驻会话**：挂起不关进程，唤醒对同一 Session 再提示；会话数有上限、闲置回收，进程重启后退化为新会话 + 续接简报（残余限制，已在文档标注）。
2. **常驻会话里的两处陈旧状态**：桥接调用了第一次运行的授权闭包（挂起后每次 `step` 都被拒），以及插件把「已挂起」记成进程级状态（第二次提示的普通文字被当成已决结束）。修法：桥接改为每次提示注入当前运行的 call，插件在 `agent/pre-step` 复位挂起标记。

## 成本（Token）已经能实测

原生运行会在每个 `assistant/message` 事件上带 `usage`（`inputTokens / outputTokens / cacheReadTokens / totalTokens`）。`test/team-native-usage-probe.mjs` 用一次极小调用确认了这一点，适配器据此把一次运行的用量求和后交给宿主结算（按**尝试**记账，因此聊天分支挂起后仍会记下这次花费；补测试「a chat branch that suspends still books the tokens it spent」）。

| 场景 | 墙钟 | 步数 | Token（实测） |
| --- | --- | --- | --- |
| 两分支串行（23:50 复跑） | 61.4 s | 5 / 6 | 37,371 |
| 两分支并行（23:50 复跑） | 13.0 s | 5 / 5 | 26,123 |
| 意图队列 → 单个执行者（23:49） | 8.2 s | 4 | 9,787 |
| 聊天挂起 → 唤醒（23:50，两提示） | 约 30 s | 7 | 18,757 |
| 两分支串行（更早一次） | 79.3 s | 9 / 7 | 31,293 |
| 两分支并行（更早一次） | 10.5 s | 5 / 5 | 26,611 |

同一次对照里并行约为串行的 1/7 墙钟，Token 也略少。这只是这一次的事实：不能外推成「并行总是省钱」，样本小、任务小，且模型采样本身波动。

## 结论边界

已证明：真实模型能在两个独立原生进程里读材料、写证据、用 `team_ask` 发起同级提问、用 `team_wait_event` 等兄弟、用 `team_answer` 回答，答复通过事件回到提问方，全程不经主 Agent 转述；同一次对照里并行显著快于串行；成本可以按尝试实测；一个聊天执行者可以跨挂起与唤醒继续同一话题。

未证明：真实 QQ 连接下的社交判断、真实 263K 压缩会话，以及多轮问答在达到 4 次上限时模型是否真的改为汇报受阻（上限本身有确定性测试）。长期成本仍只有单次样本。
