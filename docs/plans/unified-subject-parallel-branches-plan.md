# 同一主体的并行活动分支：实施 Plan

日期：2026-10-21。状态：待实施。与 [连续 QQ 主体计划](continuous-qq-subject-plan.md) 一起构成当前目标；冲突时优先采用这两份计划及用户最新要求。本文设计不代表已有生产能力。

> 实施状态（0.39.0 工作区）：§9 第 1 阶段（连续主体基线）与第 2 阶段（分支继承主体读取权、`research`/`engineer` 自建 public 视图、任务挂到活动索引）已实现；第 3 阶段（持久事件、去重、过期、订阅与确认游标、分支直接问答、原生边界投递）已实现并有确定性测试；第 4 阶段部分完成（接管 fencing、撤回、取消、重启续接已有测试，冲突合并与「主体改向推送到运行中分支」尚未接线）；第 5 阶段（真实模型并行运行、耗时/成本对照与调优）未进行。详见 [QQ 连续主体：实施状态与证据](subject-continuity.md)。

## 1. 产品契约

yoyo 是同一个主体，拥有一套身份、动机、关系、承诺与经历，可以同时关注多件事。主 Agent 和执行分支共同完成这些活动；分支是注意力与行动的延伸，不是有另一个人格的员工。

统一不要求共享全部推理文本，也不要求每次工具结果广播给所有分支。共享的是行动意图、必要背景、已确认发现和变化；临时阅读与推理上下文各自保留。不能承诺并行天然优于串行，需要通过真实任务测量延迟、成本和质量。

QQ 群和私聊允许同一主体连续理解，内容表达边界按用户要求使用提示词。主 Agent 或持有发言权的分支直接说话，不增加审核/改写 Agent。微信保持独立数据与权限域。人格一致不等于所有分支措辞完全相同，必须一致的是身份、已作承诺和事实认知。

## 2. 已有基础与差距

0.38.0 已有独立 DSH SDK 执行、peer 工具集、任务证据板、来源登记、记忆候选、team_steer、任务报告、发言租约、取消与接管。具体以接手时实际代码为准。

需补齐：主体跨窗口活动权威、分支持续收取增量变化、同级直接问答、订阅与确认游标、真实可续接生命周期、冲突合并及统一可观察性。现有按 view 限制的任务与记忆不能直接当成统一共享状态。已有 steer/report 应升级复用，不再建立一套平行消息系统。

## 3. 三类状态与一个活动索引

| 状态 | 内容 | 写入方式 |
| --- | --- | --- |
| Subject State | 身份版本、长期偏好、关系、总方向和跨活动承诺 | 主体负责语义决策；分支可提议，宿主验证版本 |
| Activity State | 目标、起因、参与者、计划、进展、等待条件、结果 | 每项有负责人；发现追加，状态更新比较 revision |
| Branch State | 临时上下文、工具游标、当前步骤、恢复点 | 分支独立维护，关键进展挂回活动 |

活动沿用连续主体计划中的 activityId。任务、动机选择、关切、计划、前瞻记忆均关联活动，不复制成几份互相竞争的真相。分支不会因为主 Agent 切换窗口而丢失活动，也不能把其他活动的临时结论覆盖为全局人格。

主 Agent 不必审核每项进展。确定的工具回执、发现、状态与用量由宿主合并；相互矛盾的结论、改方向及长期自我更新才需要主体判断。主 Agent 可以亲自聊天和研究，不成为只转发报告的瓶颈。

## 4. 分支契约与上下文继承

创建分支至少包含 branchId、activityId、parentBranchId、目标、为什么做、完成/停止条件、主体版本、活动版本、相关窗口和原文引用、能力集合、资源预算、发言租约（如有）。身份由宿主提供，不能让模型伪造自己是其他分支。

初始上下文由同一主体的人设、活动快照、相关对话片段、已确认发现、未决问题和必要记忆组成。不只给一句指令，也不默认复制全部 QQ 历史。分支可按需查询共同活动和 QQ 记忆；来源用于核对事实及场景，不按所在群制造失忆。

默认使用通用 peer 能力，按任务需要缩减工具；chat/research 等旧角色可保留为兼容预设，不作为固定人格和职责壁垒。工程分支使用独立环境，不能破坏主体 DSH 安装。

一个有用的分支可在等待后继续；不为每个群永久保留分身。活动结束后释放运行资源，将经历和恢复索引交还主体。分支可以申请协助，宿主校验总并发、深度和预算后创建同活动子分支；首期可只允许主体创建，明确标注此限制。

## 5. 快速同步协议

持久化事件字段：eventId、activityId、fromBranch、toBranch/订阅主题、kind、payload/ref、baseRevision、createdAt、expiresAt、dedupeKey。类型至少包括 finding、question、answer、progress、direction_changed、blocked、completed、cancel。

流程：写入数据库并提交 → 发进程内通知或唤醒独立 worker 桥 → 收件端读取未确认增量 → 在原生安全边界注入 → 记录 delivered/acknowledged 游标。数据库是权威，进程通知只是加速；进程重启可从游标恢复。

- 分支直接对另一分支提问、答复、发布发现；不必经主 Agent 转述。
- 普通进度按活动合并；关键发现立即通知相关订阅者，不全局广播全文。
- 正在运行：下一工具/pre-step 边界处理，不并发修改正在进行的原生请求。
- 闲置：有可行动事件才续接原生 Session；无需定时发送“继续工作”。
- cancel、撤权与所有权变化：宿主先使后续副作用失效，再请求原生取消；不能等待模型理解后才停权限。
- 更新已写入、分支已收到、模型已据此行动是三个不同状态，控制台和计量分别显示。

消息至少一次投递，通过事件 ID 去重；外部副作用另用 outbox 幂等与 uncertain 语义，不声称跨网络 exactly-once。请求/答复带关联 ID、超时和失效规则，避免无限互等或相互唤醒。对话往返、事件大小和每轮注入量设可配置上限；达限汇报 blocked，由主体决定。

宿主投递目标：同机正常负载下提交到可领取 p95 < 500ms，作为待测目标而非当前事实。实际接收目标为下一安全边界；模型响应耗时单独统计，不能算作事件总线延迟。长工具等待需可取消或有超时，不以频繁打断换取“实时”。

## 6. 冲突、发言和接管

一个步骤一个执行负责人；领取通过事务与租约，过期接管递增 generation。所有产生副作用的工具核对 generation，旧分支不能在接管后继续发送。只读研究允许主动分两条路线，不应被全局互斥串行化。

同一 QQ 目标同一时刻一个发言持有者，包含主 Agent。多个不同群可并行发言。发送绑定显式账号/目标/活动，不能使用随时变化的全局 focus 作为异步收件地址。接管先失效旧租约，再交付已发回执、未发草稿和当前话题。

发现采用追加记录与来源去重；发现互相矛盾时标记冲突并通知受影响活动，不使用最后写入者胜出。尚未确认的说法不能在另一分支变成确定事实。主 Agent 或被委派核对的分支解决冲突并发布新版本。

全局方向变化用 revision 检查；旧分支结果仍可保存为历史证据，但不能自动完成新版本目标。persona 变化在边界同步，不重启所有任务，不假称能撤回已经发出的消息。

## 7. 动机与记忆如何成为一体

动机属于主体：自己想做什么、期待什么、经历后是否满意。分支带着该意图行动，可报告新兴趣和建议，不独立优化自己的快乐分数。用户明确承诺和外部截止条件不能被一个分支擅自遗忘。

回执自动归档，分支提交经历与记忆候选，主体整理时形成共同记忆；实际观察者和来源保留。相同原文被三个分支读过不算三份独立证据，同一次成果不重复奖励动机。慢速人格学习与任务快速进展分开，不让一次局部对话立即重写全局风格。

睡眠是活动/主体调度状态，不是删除分支。某分支等待网络时，主体和其他分支可以继续。全部没有可行动工作时一起静默，相关事件再唤醒需要的执行者。

## 8. DSH 与代码改造边界

所有模型调用、工具循环和压缩继续由 DSH 原生运行，不写第二套 LLM while 循环。宿主事件路由和任务调度不属于模型循环。核对安装版本的 subagent provider 能力，再决定原生目录、消息、续接、取消能复用哪些；不伪造 capability。

- social-agent / social-store：主体连续上下文、共享活动、显式工具目标。
- team-store：扩展现有 reports/steers 为统一事件记录与投递游标，增加活动版本、分支关系与所有权 fencing。
- team-host / coordinator：订阅、路由、分支直接问答、预算与接管；保留可靠发送。
- team-native-adapter / worker-plugin：原生边界增量交付、闲置续接、取消及冷恢复；修复相同 Session 重复 create 问题。
- memory-layer / motivation：活动关联、来源去重、共同经历与主体决策。
- 控制台：同一主体下的活动/分支时间线、正在等待谁、最近事件、收件确认、实际副作用和失败。

先做最小闭环，再扩展。不要同时改写全部运行时、记忆系统和调度器；保留兼容适配并逐阶段移除旧权威。

## 9. 分阶段实施

1. **连续主体基线**：完成配套计划的切窗不失忆和直接行动；复现 xmfu 轨迹，确定当前模型/DSH 版本和生产配置。
2. **共享活动与两分支**：默认 peer；一个阅读群、一个浏览网页，同时执行并把发现增量交给主体。主 Agent 可保持另一条对话。
3. **快速交流**：复用 steer/report 做双向及同级消息；实现事件确认、合并、休眠续接、超时和取消；不靠主 Agent 轮询中转。
4. **一致性与恢复**：接管竞态、重复投递、过期结果、冲突发现、重启和压缩恢复；共同记忆去重。
5. **真实运行与调优**：测量串行/并行同任务耗时与质量；生产从两个分支开始，根据实际 CPU、内存、模型并发限制调整。当前若仍 maxConcurrent=1，必须明确它只是串行配置，不能称已验收并行。

每阶段交付代码、必要测试、架构/运维文档和已知缺口；固定提交验证与部署。保护工作区其他人的修改，数据库迁移可兼容回滚且不覆盖新消息。沿用已有授权进行 Git 提交、推送和部署；不在验收中擅自对陌生群发测试消息。

## 10. 验收矩阵

| 用例 | 必须看到的证据 |
| --- | --- |
| xmfu 观察 + 网站研究 + 主体聊天 | 至少两个分支运行时间重叠；共享同一目标与人格版本；主活动继续 |
| 研究分支发现新玩法 | 聊天分支在任务结束前收到，下一安全边界可据此行动 |
| 分支直接问答 | 有 question/answer 关联与确认，无主 Agent 转述依赖 |
| 切群、压缩、重启 | 目标、进展、未答问题与回执恢复；不重复创建既有 Session |
| 主体改变目标 | 新版本到达相关分支；旧结果不将新目标标为完成 |
| 两个分支争用同群发言 | 只允许有效 generation 的发送；目标与回执正确 |
| 相反发现 | 保留来源和冲突；未核实结论不静默覆盖 |
| 重复事件、崩溃、未知发送结果 | 状态幂等，已确认消息不重发，uncertain 明确可见 |
| 微信边界 | 所有 QQ 分支均不能读取微信数据库、凭据或 Session |
| 同任务串行与并行对照 | 报告耗时、调用数、Token 可观测情况、质量与失败；无改善时说明原因 |

完成定义：一个持续主体能有选择地分工，分支在工作中交换有用发现，主体能自然接续和接管；结果一致、消息不重复、活动不遗失。仅有多个进程、工具名称或一次最终报告都不算完成。
